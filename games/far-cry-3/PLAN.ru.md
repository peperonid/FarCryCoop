# Far Cry 3 — кампанийный ко-оп для 4 игроков: план

Русская версия плана. Английская: [PLAN.md](PLAN.md)

Статус: план, форк от Bantila/FarCryCoop 2026-11-01. Ветка `game/far-cry-3`.

## Цель

Четыре игрока проходят всю одиночную историю Far Cry 3 вместе, с катсценами, побочными
активностями (заставы, башни, охота, Путь Охотника, Розыск, испытания, гонки) и коллекционными
предметами (реликвии, письма, карты памяти). Друзья подключаются через **Steam-приглашение**.

**Версии игры:** обе поддерживаются: **1.05** (Steam depot 220241, манифест `7362101836779063707`,
DLL build 2018-05-02, последняя версия с мультиплеером, на ней сделан мод scubrah) и **1.06**
(текущая Steam / Ubisoft Connect, build 2022-10-03). У каждой версии свои адреса; общая карта
адресов строится скриптом `scripts/fc3_addrmap.py`. Серверы Ubisoft для FC3 выключены,
подключение только через наш собственный транспорт.

## Архитектура

**Транспорт A (неткод движка)** — основной путь, подтверждённый в Phase 1 RE Bantila:

- `CFCXPlayerService` движка — сетевой реплицируемый компонент с таблицей на 4 слота игрока.
  В одиночной игре слот 0 — локальный игрок. `GetNumberOfPlayers()`, `GetPlayerInSlot()`,
  `CoopTeleportPlayer` существуют и доступны из Lua.
- **Прямое подключение:** в игре есть developer quick-launch:
  `-host -login <name> -coop` (хост) и `-client -login <name> -ip <addr>` (клиент).
  Тип сессии 3 = локальный ко-оп, без сервисов Ubisoft.
- **Путь подключения:** Storm LAN discovery (`storm::echo::lan`) существует в движке,
  но PC-слой игры его не использует (только `_RdV` онлайн-провайдеры). Варианты:
  - **A1:** ASI хукает `_RdV` провайдеры, отвечает локально; сессия создаётся/принимается
    по прямому адресу через `-host`/`-client` или Storm LAN через localhost-ретранслятор
    (та же схема, что в Far Cry 1).
  - **A2:** локальный эмулятор сервиса RendezVous.
- **Запасной вариант (Транспорт B):** собственный UDP-неткод в ASI. Каждый игрок запускает
  одиночную игру; ASI отправляет состояние хоста; подключившиеся игроки — марионетки.
  Больше работы, полный контроль.

Компоненты в обоих случаях:

- `FarCry3Coop.asi` загружается Ultimate ASI Loader; хуки в `FC3.dll` / `FC3_d3d11.dll` по
  адресам, найденным через REA/Ghidra. Шаблон: `FarCryCoopNet.asi` из Far Cry (2004).
- Скриптовый слой: изменённые скрипты миссий в нашем архиве; оригинальные файлы не заменяются.
- **Steam-приглашение:** в игре нет `steam_api.dll`, поэтому переиспользуется Steam-мост
  из Far Cry (2004) (Spacewar, AppID 480): "Присоединиться" в списке друзей Steam,
  соединение через localhost. Прямой IP — запасной вариант.
- Лаунчер и лобби: лаунчер из Far Cry (2004) (Rust + Tauri) получает профиль игры, не форк.

## Фазы

0. **Идентификация игры.** Завершена 2026-10-22 (Bantila), см. [NOTES.md](NOTES.md).
1. **Исследование (read-only).** Завершена 2026-10-24 (Bantila). Распакованы данные, найдены
   скрипты миссий, сетевой слой, сервис игрока, кооп Lua API. Полные детали в NOTES.md.
2. **Спайк, выбор A или B.** Два окна игры на одном ПК (хост слева, подключившийся справа):
   оба ходят по острову, видят друг друга, стреляют в одну цель. Сначала Транспорт A:
   `-host`/`-client` с типом сессии 3 (локальный ко-оп). Если остров загружается в кооп-сессии
   с сюжетным контентом — выбираем A. Если сюжетные карты отказываются грузиться — откат на B.
   - **Проверка в игре:** два окна, оба игрока ходят по острову, видят друг друга, стреляют.
3. **Сюжетные скрипты в ко-опе.** Одиночные Domino-скрипты используют `GetLocalPlayer` и не
   знают о других игроках. План: патчить скрипты миссий в нашем архиве, чтобы скриптовые
   события (принудительные анимации, казни, места в транспорте, погони) применялись к хосту;
   остальные перемещаются или наблюдают. Не-скриптовые сегменты — свободные для всех.
   - **Проверка в игре:** первые три сюжетные миссии вместе.
4. **Катсцены.** Вступление с Ваасом и другие катсцены должны проигрываться у всех игроков.
   Система катсцен движка (xbg/seq файлы) нужен слой репликации: хост триггерит, все проигрывают.
   - **Проверка в игре:** вступление с Ваасом у всех игроков.
5. **Побочные активности.** Заставы, башни, охота, Путь Охотника, Розыск, испытания, гонки.
   Это в основном зонные активности, должны работать когда кооп-сессия запущена.
   Возможно нужны скриптовые патчи для мультиплеерных триггеров.
   - **Проверка в игре:** занять заставу вместе.
6. **Коллекционные предметы и прогресс.** Реликвии, письма, карты памяти. Реликвия,
   взятая подключившимся игроком, должна засчитываться и исчезать у хоста. Формат сохранения:
   сейв хоста — источник истины.
   - **Проверка в игре:** реликвия, взятая подключившимся игроком, засчитывается и исчезает у хоста.
7. **Масштабирование на 4 игроков.** Четыре окна, одна полная миссия. Проверить производительность,
   лаги, рассинхрон.
   - **Проверка в игре:** 4 окна, одна полная миссия.
8. **Steam-приглашение и лаунчер.** Подключение через Steam-приглашение через мост Spacewar.
   Лаунчер Rust+Tauri получает профиль FC3: путь к игре, определение версии, список игроков,
   "Старт".
   - **Проверка в игре:** подключение через Steam-приглашение.

## Риски

- Сюжетные скрипты ожидают одного Джейсона: принудительные анимации, казни, места в транспорте,
  погони. План: хост — Джейсон в скриптовых частях; остальные перемещаются или наблюдают
  короткое время.
- Сейв может быть привязан к аккаунту Ubisoft: подключившимся игрокам может нужна синхронизация
  состояния вместо копирования сейва.
- Если сетевая игра движка требует серверов Ubisoft для матчмейкинга, Транспорт A нужен
  прямой join (как в Far Cry 2004) или откат на B.
- 1.06 убрала код мультиплеера: другие адреса, возможно отсутствующие функции. 1.05 —
  основная цель; поддержка 1.06 — второстепенная.

## Кандидаты на перехват для ASI (добавлено 2026-11-07, агент; адреса 1.06 — перед применением перенести на 1.05)

Из реверс-инжиниринга только на чтение в `NOTES.md` (разделы «Путь установки кооп-id, проверенный по
сырым байтам» и «Атрибуция авторов записей»). Это **кандидаты для спайка Phase 2, не решения**; 1.05 —
основная цель, поэтому каждый адрес ниже — это адрес сборки 1.06, который надо заново найти в 1.05
скриптом `scripts\fc3_addrmap.py` перед любой правкой. Фактический перехват утверждает владелец.

Подтверждённые факты (1.06, `H:\FarCryCoop\TestFC3\bin\FC3.dll`, база образа `0x10000000`):

- Идентификатор кооп-режима — хеш `0x43521e6f`. Он же литерал в таблице mode-id: `.data 0x1216a00c`,
  `0x1216aa40`, `0x1216aee4`, `0x12173ff4`.
- Два рабочих глобала хранят установленный кооп-id: `[0x12891ca0]` и `[0x12891ca8]` (оба BSS, ноль при
  загрузке; `[0x12891ca4]`/`[0x12891cac]` — штампы инициализации). Их пишет рутина установки `0x11279910`
  (записи на `0x1127995f` и `0x11279adf`).
- У `0x11279910` нет прямого триггера: она достигается виртуальной диспетчеризацией — вирт-метод
  `0x11a58700` (слот таблицы диспетчеризации `.rdata 0x1200ad00`) → вызывающий `0x1127a0f0`/`0x11279fc0` → `0x11279910`.
- Десять глобалов `[0x12807738..0x1280775c]` подготавливаются значением `-1` при инициализации модуля
  функцией `0x11b2a610` (запись таблицы инициализации в `.rdata 0x11bd2b04` — НЕ vtable; см. NOTES
  2026-11-07). Единственный рантайм-автор записей этих глобалов — `0x117884f0`, выводящий их из
  упакованного поля `[0x1217c688]`.

Кандидаты на перехват для оценки в Phase 2 (транспорт A: форсировать локальную кооп-сессию и посмотреть,
загрузится ли остров с сюжетным контентом):

- **H1 — форсировать кооп-id на старте.** Либо (a) заNOPить страж установки и из ASI записать `0x43521e6f`
  в `[0x12891ca0]`/`[0x12891ca8]` после поднятия движка, либо (b) перехватить цепочку вирт-метода установки
  (диспетчер `0x1200ad00` → `0x11279910`) и форсировать id. Выбор в пользу записи двух глобалов: это
  наименьшее наблюдаемое изменение.
- **H2 — (сомнителен, скорее убрать).** `0x11b2a610` — однократная заглушка инициализации модуля (не
  по-сессионный метод), поэтому не выполняется при разрушении сессии — перезагрузка, подготавливающая
  `[0x12807738..0x1280775c]`, не является той угрозой, что предполагалась при наброске этого хука.
  Глобалы кооп-id `[0x12891ca0]/[0x12891ca8]` — другой набор. Пересматривать только если рантайм-трассировка
  покажет, что `[0x12891ca0]` действительно затирается.

Открыто до того, как любой перехват станет реальным (отмечено в NOTES): вызывающий вирт-метода
`0x11a58700` (владелец таблицы `.rdata 0x1200ad00` определён — `CFCXPlaylistService`; `0x11bd2b04`
определён — таблица инициализации, не vtable). Пока вызывающий `0x11a58700` не известен, перехваты —
эксперименты «писать после инициализации», а не устойчивые обходы.


## Статус хуков после сессий 5–6 (добавлено 2026-11-08, агент; заменяет формулировку H1 выше)

NOTES 2026-11-08 (сессии 5 и 6, зонды `p300`–`p315`) изменили понимание переключателя ко-опа. Это
дополнение перекрывает формулировку H1 из раздела выше; адреса там остаются верными — неверным стал *выбор
переменной для записи*.

- **H1 понижен: запись `[0x12891ca0]`/`[0x12891ca8]` (`0x43521e6f`) не может переключить живой режим.**
  Эти две глобальные — локальные в функции `static const` константы-ключи запроса (байты метки инициализации
  `[0x12891ca4]`/`[0x12891cac]`), на каждую ровно 3 ссылки в `.text`, все внутри установочных процедур
  `0x11279910` / `0x11279a2b`. Никакой игровой код/диспетчер не читает их по адресу. Запись в них из ASI меняет
  лишь константы, которые установщик использует как ключи поиска, поэтому H1 **по построению НЕОДНОЗНАЧЕН**
  (движок и так держит там `0x43521e6f`). Можно оставить как безопасный диагностический зонд, но это не рычаг.
- **Живой id текущего режима — поле менеджера режимов `[this + 0x4c]`** (`this` в `ebx`), а не глобальная.
  Диспетчеризация в `FC3.dll 0x113405a0` читает его и сравнивает с шестью hash-id режимов —
  `0xab4fc8e2, 0x43521e6f`(CO-OP)`, 0x9991daec, 0x6c2b3868, 0xf66ffb87, 0x2100ced7` (три цепочки в
  `0x113405a0`, `0x11340622`, `0x11340a25`). Все шесть ведут в блок главного меню / `IngameToLobby`;
  `0x2100ced7` — единственный id, который ещё грузит текстуры загрузки по мирам (`CustomMap`,
  `UI\Multiplayer\Textures\Menu\Loading\Worlds\`).
- **Живое состояние ко-оп-сессии — контейнер плейлист-сервиса `[service + 0x8c0]`**, сервис = синглтон
  `CFCXPlaylistService` (глобальный экземпляр `0x12863890`, геттер `0x103d1640`). Ко-оп-сессия — запись
  `PrivateCoopPlaylist` (`0x11fab710`) в этом контейнере. `0x43521e6f` встречается в 11 местах `.text`
  (настоящие потребители) — см. NOTES, сессия 5.

Исправленное направление Фазы 2 (заменяет «принудить id ко-опа на старте»):

- **H3 — новое основное направление.** Трассировка в рантайме (отладчик владельца, статической альтернативы не
  найдено): поставить точку останова на авторе записи в `[this + 0x4c]` менеджера режимов, чтобы узнать, кто
  ставит живой режим и по чему, и обойти `[service + 0x8c0]`, чтобы прочитать живой контейнер плейлистов. Это
  единственный путь к локальной ко-оп-сессии; офлайн-записи в глобальные исчерпаны.
- **H1 — оставить только как безопасный диагностический зонд.** Запись установочных глобальных оставить в зонде
  исключительно чтобы подтвердить, что цепочка запускается; изменения поведения от неё не ожидается.
- **Всё ещё заблокировано:** чтобы назвать пять не-кооп hash-id режимов, нужен восстановленный самодельный хеш
  id Dunia (FNV/djb2/sdbm/murmur отброшены) либо таблица имя↔id из `GameModesConfig.xml`; офлайн-подбор не работает.

## Статус точек перехвата после сессии 7 (добавлено 2026-11-08, агент; уточняет H3 выше - теперь статически, не только трассировкой)

Сессия 7 выгрузила псевдокод из офлайн-проекта Ghidra `FC3_106` (см. NOTES.md сессия 7). Это повышает
H3: механизм переключения теперь закреплён статически; трассировка свелась к получению указателя `this`
менеджера режимов.

- **«Виртуальный метод переключения режима» - это `modeManager->vtable[+0x5c]`** (вызов
  `(**(code **)(*param_1 + 0x5c))(&id)` внутри `FUN_11340560`, тело `[0x11340560,0x113409cd]`).
  Диспетчер читает `[this+0x4c]` (подтверждает находку сессий 5-6), заменяет любой из шести id на
  **id лобби `0x63ddbbcb`**, если строка назначения равна `FUN_11788030("FCXMainMenu")`, и затем зовёт
  этот виртуальный метод. `[this+0x74]` гейтит ветку текстур загрузки мира.
- **Наполнить co-op-сессию без UI:** `FUN_1127a0f0(service)` (где `this` = сервис) строит контейнер
  `[service+0x8c0]` через `FUN_1025f3f0`, затем запускает инсталлер `FUN_11279910`, который ищет co-op
  запись **по ключу `0x43521e6f`** через `FUN_113224e0` и добавляет её в контейнер через
  `container->vtable[+0x5c]`. Подтверждает, что `[service+0x8c0]` живой (заполняется во время выполнения).
- **Поправка к заметке о синглтоне:** `FUN_103d1640` возвращает `&DAT_12863890` - экземпляр это сам
  объект ПО адресу `0x12863890` (C++ magic-static под защитой `0x1286388c`), а не указатель, хранящийся
  там. То есть `this` сервиса = `module.base + (0x12863890 - 0x10000000)` напрямую; не делать
  `readPointer()`. Исправлено в `scripts/fc3_h3_trace.js`.

Уточнённые рычаги фазы 2 (оба теперь статические):
- **H3a - переключить режим:** записать `[modeManager+0x4c] = 0x43521e6f` и вызвать
  `modeManager->vtable[+0x5c](0x43521e6f)`. Нужен только живой `this` менеджера режимов (одно чтение
  `ebx` по `0x113405a0` через Frida).
- **H3b - наполнить сессию:** вызвать `FUN_1127a0f0` (или точнее `FUN_113224e0`(0x43521e6f), затем
  `container->vtable[+0x5c]`) на сервисе плейлистов, чтобы внедрить co-op-запись.
- По-прежнему заблокировано: именовать пять соседних mode-hash id (кастомный хеш не восстановлен).

## Статус хуков после сессии 8 (добавлено 2026-11-08, агент; ПЕРЕОПРЕДЕЛЯЕТ H3a выше)

Сессии 8/8b/8c сняли живой менеджер режимов (Frida на DX9 `farcry3.exe`, только рабочая копия) и
декомпилировали виртуал переключения. Два жёстких результата меняют H3a:

- **Первичная таблица виртуалов живого менеджера — `0x1200e5f8`; диспатчер `FUN_11340560` — это его слот
  `+0x60`, а `vtable[+0x5c]` — это `FUN_1030f8a0`.** `FUN_1030f8a0` декомпилируется в двухстрочную
  перестановку id: `[this+0x4c]=[this+0x48]; [this+0x48]=*param_2`. Она не грузит мир и не строит сессию.
  **Значит H3a (записать `[this+0x4c]` + вызвать `vtable[+0x5c]`) — no-op для входа в co-op**: безвреден
  (нет риска падения, поэтому живой тест `switch go` не нужен), но запустить co-op-сессию не может.
  «Переключатель» лишь кладёт целевой id в `[this+0x48]`; реальный переход — в потребителях `[this+0x48]`
  и у того, кто дёргает виртуал диспатчера `vtable[+0x60]` с `(param_2=&destId, ...)`.
- **Живой менеджер надёжно находится только хуком диспатчера** (`--watch` во время перехода): id
  `[this+0x4c]`/`[this+0x48]` транзитны и никогда не входят в шестёрку; объект НЕ ищется сканом по vptr
  (его первичный vptr `0x1200e5f8` никогда не сканировался; `0x1200e620` — вторичный подобъект по
  первичная+0x28). `[service+0x8c0]` (co-op-плейлист) остаётся `0x0` даже внутри загруженного одиночного
  мира, а UI co-op-a гейтится сетевым сервисом Ubisoft, офлайн недоступным (игра пишет «Служба сетевой игры
  больше недоступна» и обрывает смену режима).

Пересмотренное направление Фазы-2:
- **H3a не развивать.** Установщик id не вводит в co-op.
- **Одного H3b (populate), вероятно, тоже мало**: даже с собранным `[service+0x8c0]` ни один офлайн-потребитель
  не переводит `[this+0x48]` в co-op-мир, т.к. нет предпосылки-нетплея.
- **Новая основная зацепка H4: снять реальный заход в co-op ОНЛАЙН** (владелец делает настоящий 2-игрока co-op
  заход под трейсером), записать последовательность вызовов виртуала диспатчера + состояние сервиса
  плейлиста/нетплея, и реконструировать её для офлайн/4p. Статические xref не достают точку перехода
  (непрямой вирт-вызов), потому надёжная карта — только трассировка УСПЕШНОГО захода.
- Вторично (опционально): найти офлайн-потребителей `[this+0x48]`, чтобы понять, есть ли одна функция,
  поднимающая мир/сессию по co-op целевому id.

### Обновление сессии 8d (итог офлайн H4b)

Офлайн-поиск (FindModeConsumers/DecompileConsumers по FC3_106) нашёл настоящий запуск co-op-режима:
**`FUN_10fa1990`** (`__thiscall` по менеджеру режимов; ядро перехода `FUN_11340d00`). По co-op-id
`0x43521e6f` пишет `"Coop_Fenrir_Loading"`. Кроме `this` нужны: обёртка co-op-id (`param_2`),
co-op **дескриптор** (`param_3`, строка имени карты/мира в `+0xC`, проверяется `FUN_10003f00`),
предикат доступности **`FUN_1011cb30()`** = true и живой хэндл сессии в `DAT_12804acc+0x68` /
плейлисте `svc+0x8c0`. Первичная таблица виртуалов менеджера `0x1200e5f8` (конструктор `FUN_10fa1eb0`;
+0x50 геттер, +0x5c перестановка id, +0x60 диспатчер — подтверждено). **Офлайн-итог:** дескриптор и
сессия/плейлист создаются онлайн-лобби, которое офлайн ненаблюдаемо (`svc+0x8c0` остаётся `0x0`
в мире, нетплей офлайн выключен), поэтому `FUN_10fa1990` доходит до `"Coop_Fenrir_Loading"` и дальше
грузить нечего. H4 остаётся единственным путём к реальному переходу; вторичная офлайн-зацепка
(ядро `FUN_11340d00` + сможет ли поддельный дескриптор пройти `FUN_1011cb30`) — остаточная офлайн-
находка.
